# Прокси для Телеграм бесплатно — проверенный список MTProto прокси

Бесплатный открытый **список прокси для Телеграм**: рабочие **MTProto / MTProxy** прокси
(FakeTLS `ee`, secure `dd` и обычные), список пересобирается примерно каждые 15 минут на
GitHub Actions. Нажмите на ссылку — Telegram подключится сам, без лишних приложений и
регистрации. Для тех, у кого Telegram заблокирован или работает медленно. Работает в Telegram
на Android, iPhone и Desktop. Проект не связан с Telegram.

<a id="start-here--one-line"></a><a id="quick-start"></a>

## 🚀 Начните отсюда — одно касание или одна строка

**На телефоне самый короткий путь — [живая панель](https://0xradikal.github.io/Free-Telegram-Proxy/):**
каждая строка открывается прямо в Telegram, он покажет параметры прокси — останется нажать
**«Подключить прокси»**. Ничего не нужно копировать, и кроме Telegram ничего не нужно.

**Top 100** — самый короткий список: он берётся из `resilient` (одна ссылка на IP сервера),
сортируется по доказанной стабильности, затем по времени отклика, обычно не больше 5 ссылок на
одну сеть — и каждая его строка уже передала настоящий запрос в дата-центр Telegram во **всех
трёх** раундах проверки.

```text
https://raw.githubusercontent.com/0xRadikal/Free-Telegram-Proxy/main/top100.txt
```

Нужны все различные серверы, а не 100? Берите `resilient` — тот же уровень доказательств, по
одной кликабельной ссылке `https://t.me/proxy?…` на каждый IP сервера:

```text
https://raw.githubusercontent.com/0xRadikal/Free-Telegram-Proxy/main/resilient/tme.txt
```

<a id="how-to-connect"></a>

### 📲 Как подключить прокси в Телеграм

Это обычные списки ссылок, а не «подписка» (subscription), которую импортирует приложение.

1. **Android и iPhone:** откройте [`top100.txt`](https://raw.githubusercontent.com/0xRadikal/Free-Telegram-Proxy/main/top100.txt)
   или [`resilient/tme.txt`](https://raw.githubusercontent.com/0xRadikal/Free-Telegram-Proxy/main/resilient/tme.txt)
   на телефоне и нажмите на любую строку. Telegram откроется — нажмите **«Подключить прокси»**.
   Если ссылка не кликается, отправьте строку себе в **«Избранное»** и нажмите на неё там.
2. **Telegram Desktop (Windows, macOS, Linux):** нажмите на ссылку `tg://proxy` или
   `https://t.me/proxy`, или откройте **Настройки → Продвинутые настройки → Тип соединения →
   Использовать собственный прокси → Добавить прокси** и выберите MTProto.
3. **Вручную на телефоне:** **Настройки → Данные и память → Настройки прокси → Добавить
   прокси**, тип MTProto, затем введите сервер, порт и секрет.
4. **Не подключается?** Попробуйте следующую строку: блокировки закрывают одни прокси и не
   трогают другие.

Названия пунктов меню взяты из официального русского перевода Telegram на
[translations.telegram.org](https://translations.telegram.org/ru/); в разных версиях
приложения они могут немного отличаться.

# ⚡ Списки прокси

> **Не знаете, какой взять?** Берите `top100.txt` — 100 доказанных ссылок из разных сетей.
> Нужны все проверенные серверы, по одной ссылке на каждый? Берите `resilient`:
>
> ```
> https://raw.githubusercontent.com/0xRadikal/Free-Telegram-Proxy/main/resilient/tme.txt
> ```
>
> Нужен самый большой список, а не самый полезный? `verified` хранит все псевдонимы каждого
> сервера — много ссылок, но гораздо меньше машин (см. [воронку](#live-verification-snapshot)).

## 🎛️ Выберите уровень

тот же пул, отфильтрованный по тому, сколько есть доказательств, что прокси действительно
работает**, и по тому, сколько разных машин за ним стоит.

**Какой формат?** `tg.txt` содержит ссылки `tg://proxy?…`, которые приложения Telegram
открывают напрямую. `tme.txt` — тот же список в том же порядке, но в виде веб-ссылок
`https://t.me/proxy?…`; они кликабельны почти везде, где кликабелен URL. `proxies.json` — тот же
список в виде структурированных строк (`server`, `port`, `secret`, `type`, `ip`, `country`,
`asn`, `asn_org`, `rtt_ms`, `uptime`, `checks`, `sources`). Перед публикацией все три формата
сверяются друг с другом (см. [ниже](#release-checks)). Старый `top50.txt` сохранён для
существующих пользователей — это первые 50 строк `top100.txt`.

## 🎯 Ссылки по типу секрета и по стране

У трёх форматов секрета есть свои уровни (`faketls/`, `secure/`, `classic/` выше). По странам —
один файл на каждую страну **сервера**, `countries/<CC>.txt` (ссылки `tg://`, одна на IP
сервера, из `resilient`):

```text
https://raw.githubusercontent.com/0xRadikal/Free-Telegram-Proxy/main/countries/DE.txt
```

Файл публикуется **только если он не пустой**, поэтому 404 означает «в этот раз ничего такого
нет» — и никогда не пустой файл, который молча заменил бы уже сохранённый у вас список. Страна —
это место, где по данным DB-IP стоит **сервер** прокси, а не обещание, что он работает *из*
этой страны. Актуальный список существующих файлов стран — блок `countries` в
[`index.json`](#machine-readable); живой снимок [ниже](#live-verification-snapshot) ссылается
на двенадцать самых больших.

<a id="how-a-proxy-is-tested"></a><a id="how-verification-works"></a>

# 🧪 А это вообще работает?

Большинство бесплатных списков прокси публикуют одно большое число и оставляют вас гадать. Вот
неудобный ответ, **измеренный, а не оценённый**: значительная часть любого публичного пула
MTProto в каждый момент мертва, а многое из того, что *работает*, — это **одни и те же несколько
машин под множеством имён**: один сервер может скрываться за сотнями поддоменов или секретов. Это
свойство публичных списков прокси, а не этого репозитория, поэтому вместо того чтобы это прятать,
каждый запуск это измеряет и публикует оба числа: **проверенные ссылки** и **реальные серверы**.

<a id="why-this-project-exists"></a>

<p align="center"><img src="assets/readme/principles.svg" width="100%" alt="Три инженерных принципа Raydikalx: проверка, разнообразие, прозрачность" /></p>

Каждая ссылка проходит через эти этапы. Каждый этап достаточно дешёв, чтобы прогнать через него
весь пул, и каждый отсеивает то, на что следующий этап потратил бы время впустую:

<picture><source media="(max-width: 600px)" srcset="assets/readme/pipeline-mobile.svg" /><img src="assets/readme/pipeline.svg" width="100%" alt="Пятиэтапный конвейер проверки MTProto: сбор, нормализация, проверка, ранжирование, публикация" /></picture>

| Этап | Какой вопрос он задаёт | Стоимость |
|:--|:--|:--|
| **Разбор** | Разбирается ли секрет ровно так, как его разбирает TDLib (собственная библиотека Telegram)? | без сети |
| **DNS** | Резолвится ли имя хоста — и **все ли** адреса публичные? | один DNS-запрос на хост |
| **TCP / FakeTLS** | Принимает ли порт соединение? Для секретов `ee`: верен ли HMAC в ServerHello для *нашего* секрета? | одно подключение на каждую уникальную тройку `(ip, port, secret)` |
| **Передача в DC** | Отвечает ли **настоящий дата-центр Telegram на `req_pq_multi` через прокси**, возвращая только что сгенерированный нами nonce? | полное рукопожатие, **3 раза** |
| **Ранжирование** | Какие ссылки прошли *каждый* раунд на *каждом* адресе — и какие из них одна и та же машина? | только сортировка |

Ссылка попадает в `verified/`, только если прошла **каждый** раунд — а не лучший из них. Если имя
хоста резолвится в несколько IPv4-адресов, должен пройти **каждый** адрес: клиент Telegram
подключается к тому адресу, который резолвер вернёт первым, а DNS с round-robin меняет этот
порядок от пользователя к пользователю.

<a id="release-checks"></a>

# ✅ Каждый релиз проверяется перед публикацией

Список, который *почти* правильный, — ловушка: строка, которая не разбирается, молча
пропускается, а строка JSON, расходящаяся с текстовым файлом, отправит приложение не на тот
сервер. Перед любой публикацией [`tools/validate_outputs.py`](tools/validate_outputs.py) заново
проверяет каждый сгенерированный файл:

- каждая строка каждого `tg.txt` / `tme.txt` **заново разбирается** тем же парсером, точно
  повторяющим TDLib;
- `tg.txt` и `tme.txt` одного уровня описывают **одни и те же прокси в одном и том же порядке**,
  а `proxies.json` совпадает с ними построчно;
- **ни один файл уровня не пуст**, а `index.json` объявляет **ровно** те файлы, которые
  существуют;
- `resilient/`, `fast/`, `stable/`, `faketls/`, `secure/`, `classic/` содержат **не больше одной
  ссылки на IP**;
- `top100.txt` — подмножество `resilient/`, не повторяет ни ссылок, ни IP, соблюдает заявленное
  ограничение по сетям, а `top50.txt` — ровно его первые 50 строк.

Затем [`tools/check_size.py`](tools/check_size.py) проверяет бюджет размера (всего 4 МиБ,
1 МиБ на файл). Если любая проверка не проходит, **запуск прерывается и ничего не коммитится** —
предыдущий хороший релиз остаётся на месте.

Сам проверяющий модуль тестируется на настоящих вещах, а не на заглушках, на раннере GitHub при
каждом pull request:

```bash
python -m pytest -q -rs     # unit · TDLib differential · live integration
```

- **Положительный контроль:** эталонный прокси-сервер
  [alexbers/mtprotoproxy](https://github.com/alexbers/mtprotoproxy), включённый без изменений на
  фиксированном коммите (`bd5b03c`), должен проходить во всех трёх режимах секрета и через каждый
  боевой DC Telegram.
- **Отрицательные контроли:** неверный секрет, один изменённый бит в секрете, маскирующий сервер
  с неверным секретом, закрытый порт и настоящие интернет-серверы, которые не являются прокси, —
  всё это обязано не пройти.
- **Дифференциальный тест:** разбор секретов сравнивается с настоящей TDLib (`tdjson`) на корпусе
  всех секретов, которые проект когда-либо собрал.
- **Сквозной тест:** отдельная CI-задача прогоняет весь конвейер на живых источниках (два коротких
  раунда), а затем те же валидаторы, что использует публикация, — при этом ничего не пушится.

> ⚠️ **Пройти проверки — не то же самое, что работать у вас.** Валидаторы доказывают, что файлы
> согласованы; проверка доказывает, что прокси передал запрос *с раннера*. Доступен ли он из вашей
> сети — другой вопрос, на который снаружи никто ответить не может; см. [воронку выше](#how-verification-works).

## 🏷️ Стабильные идентификаторы, выведенные из содержимого

У ссылок MTProto нет поля «имя», поэтому ничего не переименовывается. Стабильной должна оставаться
**идентичность** прокси: каждый прокси отслеживается как `sha256(server|port|secret)[:12]` —
**выведено из самого прокси, а не из его позиции в списке**, — поэтому его история проверок
переживает перестановки и повторный сбор между запусками.

То же касается ссылки, которая представляет IP сервера в `resilient/` и в построенных из него
уровнях: это псевдоним с **самой длинной историей проверок** (при равенстве — по серверу, порту и
секрету), а не самый быстрый. Выбор по скорости менял опубликованную ссылку для **31 из 313** IP
между двумя соседними запусками — та же машина, другая строка в вашем сохранённом списке, без
всякой пользы.

# 🗂️ Структура репозитория

**Одна ветка — `main`.** Исходный код и опубликованные результаты лежат рядом в ветке по

Генерируется машиной, обновляется при каждом запуске (около 50 файлов; число файлов стран

fast/        tg.txt · tme.txt · proxies.json   fastest 25 % of resilient
faketls/     tg.txt · tme.txt · proxies.json   ee secrets, one per IP
secure/      tg.txt · tme.txt · proxies.json   dd secrets, one per IP
classic/     tg.txt · tme.txt · proxies.json   plain secrets, one per IP
all/         tg.txt                            everything collected, including failed

state.json   per-proxy check history · per-source yield history
README.md · README_FA.md · README_RU.md   templates/ + the live block
```

Написано людьми, с обычной историей git и blame:

```
tgproxy/        the pipeline — sources · fetch · links · secret · netinfo · probe
                pipeline · state · publish · readme
tests/          unit, TDLib differential and live integration tests
                (+ refserver/: the pinned reference MTProxy server)
tools/          validate_outputs · check_size · check_freshness · … · server/ (15-minute trigger)
templates/      the README templates (the bot fills in the live block)
assets/readme/  the images used in this README
docs/           the live dashboard, methodology and data guide (GitHub Pages)
.github/        workflows (update · ci · pages · publication-health) · forms · Dependabot
SECURITY.md · CONTRIBUTING.md · ACCESSIBILITY.md · CODE_OF_CONDUCT.md · SUPPORT.md
CITATION.cff · LICENSE

Два правила, которые легко пропустить и которые очень важны:

- **Пустые файлы никогда не публикуются.** Уровень, страна или топ-список появляются, только если
  в них что-то есть; пустой в этом запуске — удаляется. Пустой файл был бы *хуже* 404: скрипт или
  приложение, обновляющееся из него, заменило бы рабочий список пустотой, а при 404 оно оставляет
  то, что уже есть.
- **`index.json` объявляет ровно те файлы, которые существуют** — иначе валидатор отклоняет
  запуск, так что его список адресов никогда не обещает того, чего в репозитории нет.

<a id="publishing"></a>

# 🌿 Как публикация остаётся дешёвой (и почему файлы лежат в `main`)

Git никогда не забывает blob. Каждый запуск по расписанию заново генерирует один и тот же набор
файлов, и если обычным способом добавлять их в ветку, в историю навсегда попадает **новая копия**
каждого изменённого файла. Тогда стоимость публикации — **O(число запусков)**, без верхней
границы. При ~96 запусках в сутки это не теоретическая проблема.

### ❌ Соблазнительное решение (здесь не используется)

Вынести результаты в **orphan-ветку**, которую каждый раз перезаписывают одним коммитом через
force-push. Стоимость падает до O(1) — и проект ломается для пользователей: каждая скопированная
ссылка `…/main/top100.txt` отдаёт 404, посетитель репозитория вообще не видит прокси, а
поисковики индексируют ветку по умолчанию. Соседний проект
[Free-v2ray-Configs](https://github.com/0xRadikal/Free-v2ray-Configs#-how-publishing-stays-cheap-and-why-the-files-live-on-main)
попробовал именно это и откатил; этот репозиторий использовал правильное решение с первого
запуска.

### ✅ Правильное решение — скользящий squash в `main`

Результаты публикуются **в ветку по умолчанию**, но ветка всегда остаётся в виде
*история исходников + ровно один коммит с результатами*:

1. Найти самый новый коммит, **не** помеченный `[auto-output]`, — это **якорь**.
2. Собрать дерево = *дерево якоря* + *свежие результаты этого запуска*.
3. `git commit-tree <tree> -p <anchor>` и push **с lease**.

Предыдущий коммит с результатами становится недостижимым и удаляется сборщиком мусора. Это видно
прямо в логе — коммиты строго чередуются, один коммит с результатами на один коммит человека, сколько
бы запусков ни прошло между ними:

```
63348c7  bot    chore: update proxies — 2026-10-28 15:57 UTC — 1919 verified / 409 servers   ← the only live output
992dbd3  human  docs(readme): V14 brand SVG series …
967e1c3  bot    chore: update proxies — 2026-10-28 15:41 UTC — 1941 verified / 417 servers
28a5bcc  human  docs(readme): V11 branded README …
```

Стоимость публикации — **O(1)**, а каждый файл остаётся ровно там, где его уже ищут пользователи
и поисковые роботы.

Каждое из свойств безопасности ниже обеспечивается шагом публикации в
[`update.yml`](.github/workflows/update.yml):

- **`--force-with-lease`, никогда не голый `--force`.** Публикация идёт в ту же ветку, куда
  коммитят люди, поэтому наивный force-push мог бы удалить их работу. С lease спорный push
  отклоняется, шаг заново находит якорь и повторяет попытку (до 5 раз).
- **Защита от регрессии исходников.** Проверяется каждый путь, отличающийся между якорем и
  вершиной; если изменилось что-то вне набора результатов, шаг отказывается публиковать, вместо
  того чтобы откатить чей-то код.
- **Учёт неглубокого checkout.** Checkout загружает только 2 коммита; если якоря среди них нет,
  шаг постепенно углубляется (2 → 4 → 8 → 32 → 128), пока не найдёт его, вместо того чтобы
  клонировать всю историю каждые 15 минут.
- **Отказ по умолчанию везде.** Отсутствие `index.json`, `health.json`, `verified/`,
  `resilient/` или топ-списков, проваленный валидатор, превышенный бюджет размера или дерево без
  ключевых исходных файлов — публикация прерывается, а предыдущий хороший релиз остаётся на месте.
- **Никакой рекурсии.** У workflow обновления нет триггера `push`, бот никогда не пишет пути,
  запускающие CI или Pages, а push, сделанный с `GITHUB_TOKEN`, не запускает новые workflow.

### 🧊 Результаты намеренно детерминированы

Скользящий squash ограничивает историю; детерминированность делает diff каждого раунда честным.
Тест проверяет, что одни и те же данные дают одни и те же байты. Источники бессмысленных
изменений, найденные измерениями и устранённые:

| Было | Стало |
|:--|:--|
| IP представлял самый быстрый псевдоним — шум RTT менял опубликованную ссылку для 31 из 313 IP между двумя соседними запусками | Побеждает псевдоним с **самой длинной историей проверок**; при равенстве — по серверу/порту/секрету |
| Рекомендуемый список сортировался только по RTT — соседние запуски из США совпадали лишь в 24–25 из 50 позиций | Сортировка сначала по **доказанному аптайму** (нижняя граница Уилсона по истории проверок), RTT лишь разрешает равенство |

Строки сортируются по ключу, выведенному из содержимого (измеренный RTT, затем сервер/порт/секрет;
`all/` — по серверу/порту/секрету), а не по порядку прихода сетевых ответов. Детерминированность
**не** означает, что файлы перестают меняться: RTT и «прошёл/не прошёл» измеряются заново при
каждом запуске. Она означает, что файлы меняются *только когда меняются измерения*.

### 🩹 Одна честная оговорка

Коммит с результатами, на котором построен коммит человека, остаётся в истории навсегда (поэтому
в логе выше всё ещё виден `967e1c3`). Значит, история растёт на один снимок результатов **на
каждый коммит человека**, а не на каждый запуск — сейчас репозиторий занимает меньше 3 МБ. Ничего
никогда не переписывается; существующие клоны и ссылки остаются рабочими.

# 🩺 Состояние источников и отчёт о проверке — `health.json`

```
https://raw.githubusercontent.com/0xRadikal/Free-Telegram-Proxy/main/health.json
```

Пересобирается при каждом запуске. Для каждого из 24 источников записываются `status` (`ok` /
`empty` / `fail`), HTTP-код, число попыток, задержка, сколько прокси он перечислил, сколько из
них прошли проверку, и последняя ошибка — так что мёртвый или изменившийся источник виден сразу,
а не просто молча уменьшает результат.

Числа берутся с машины, которая сделала релиз, а не из этого README. Вот файл из снимка выше, в
сокращении:

```jsonc
{
  "updated": "2026-10-28T15:54:58Z",
  "runner": { "loc": "US", "colo": "ORD" },        // where the test ran from (never its IP)
  "per_round_ok_targets": [984, 948, 936],          // distinct targets that passed, per round
  "timings_s": { "fetch": 0.79, "dns": 37.13, "probe": 88.92 },
  "reasons": { "tcp:timeout": 671, "dns": 281, "tcp:ConnectionRefusedError": 227,
               "tls:bad-hello": 134, "eof": 80, "flaky": 19 /* … */ },
  "sources": [
    { "id": "tgmtproxy", "kind": "github", "status": "ok", "http": 200, "attempts": 1,
      "ms": 253, "found": 900, "verified": 895, "exclusive_verified_servers": 50,
      "error": null }
    /* … 23 more … */
  ],
  "operators": [ { "asn": 24940, "org": "Hetzner Online GmbH", "links": 399 } /* … */ ],
  "geoip": "DB-IP Lite (CC BY 4.0)"
}
```

Три детали, которые стоит знать:

- **`runner`** — страна и Cloudflare colo, откуда шла *проверка*; это самая важная оговорка при
  чтении любого процента успеха. IP-адрес раннера намеренно никогда не публикуется.
- **`reasons`** называет причину отказа для каждой отброшенной ссылки (в ссылках; в снимке они в
  сумме дают ровно 1 546 непроверенных ссылок), так что источник, начавший выдавать мусор,
  становится заметен, а не просто тихо уменьшает результат.
- **`exclusive_verified_servers`** считается по принципу leave-one-out: это проверенные серверы,
  которые исчезли бы, если убрать этот источник. Только это число оправдывает место источника в
  списке.

# ⚙️ Как это работает

1. **Загрузка** — 24 источника скачиваются параллельно: 16 raw-файлов с GitHub и 8 публичных
   Telegram-каналов, которые читаются через их публичный веб-просмотр (без входа и без API-ключа).
   Временные ошибки повторяются, но на первом 4xx загрузка останавливается, так что мёртвый адрес
   *попадает в отчёт*, а не засыпается повторными запросами.
2. **Разбор** — каждый секрет разбирается по точным правилам TDLib (обычный, `dd`, `ee`; hex и
   base64). Всё, что отверг бы сам Telegram, отбрасывается здесь.
3. **Дедупликация** — ссылки объединяются по `(server, port, secret)`; запоминается каждый
   источник, который перечислил прокси, — именно это делает возможной статистику leave-one-out.
4. **DNS** — каждое имя хоста резолвится; любой непубличный адрес отклоняет ссылку, и проверяется
   каждый IPv4-адрес, а не только первый.
5. **Проверка ×3** — TCP, где нужно — HMAC FakeTLS, затем `req_pq_multi`, переданный в DC
   Telegram, и проверка нашего nonce в ответе. Три раунда с интервалом 20 с; каждая уникальная
   цель набирается один раз за раунд, а уже провалившиеся ссылки больше не набираются.
6. **Память** — для каждого прокси в `state.json` дописывается один бит «прошёл/не прошёл»
   (последние 96 запусков, около суток; прокси, не встречавшиеся 7 дней, забываются).
7. **Ранжирование** — `verified` → одна ссылка на IP (`resilient`) → `stable`, `fast`, уровни по
   типу секрета, страны (DB-IP Lite) и Top 100 с ограничением по сетям.
8. **Публикация** — валидаторы и бюджет размера, коммит скользящего squash в `main`, очистка кеша
   jsDelivr и живой блок этого README.

<a id="scheduling"></a>

## ⏱️ Надёжное расписание ~15 минут

Cron `schedule:` в GitHub работает по принципу «как получится» и в часы нагрузки часто
задерживается или пропускается. Чтобы всё равно держать ровный ритм, в этом репозитории **три
уровня**:

1. **`repository_dispatch` от серверного таймера** — крошечный постоянно работающий таймер systemd
   раз в 15 минут отправляет одно событие `update-now`. Больше он ничего не делает: весь сбор,
   проверка и публикация идут на GitHub Actions. Из последних 100 запусков обновления 95 были
   запущены так и 5 — по cron, все успешные.
2. **Проверка свежести** — каждый запуск сначала читает `index.json` с удалённой вершины и сразу
   завершается, если ему меньше 13 минут (8 минут для события от таймера), так что идущие подряд
   триггеры схлопываются в один запуск: ни лишних запусков, ни двойных обновлений.
3. **Резервный cron GitHub** (`4,19,34,49 * * * *`) — не в начале часа, чтобы список продолжал
   обновляться, если сервер недоступен. Поддерживается и ручной `workflow_dispatch` (с
   необязательным `force`).

Отдельный сторож только для чтения ([`publication-health.yml`](.github/workflows/publication-health.yml))
дважды в час проверяет опубликованные результаты и открывает одно issue `stale-output`, если они
устарели или некорректны, а после восстановления закрывает его автоматически.

<a id="faq"></a><a id="frequently-asked-questions"></a>

## ❓ Частые вопросы

<details>
<summary><strong>Это бесплатные прокси для Телеграм?</strong></summary>

Да. Списки общедоступны, не нужны ни аккаунт, ни регистрация, ни оплата. Для подключения нужен
только сам Telegram.

</details>

<details>
<summary><strong>Почему проверенный прокси иногда не подключается?</strong></summary>

Проверка доказывает сквозное соединение **с сервера проверки во время проверки**, а не
доступность у вашего оператора или в вашей стране. Попробуйте другой недавно проверенный сервер
или другой уровень.

</details>

<details>
<summary><strong>Как часто обновляется список?</strong></summary>

Примерно каждые **15 минут** — в зависимости от GitHub Actions, публичных источников и состояния
сети. Фактическое время последней публикации — `updated` в живом блоке или в
[`index.json`](index.json).

</details>

<details>
<summary><strong>Как обрабатываются фальшивые, повторяющиеся и мёртвые прокси?</strong></summary>

Каждая ссылка проверяется по ответу настоящего дата-центра в три раунда; в `verified/` остаются
ссылки, прошедшие все раунды, а `resilient/` убирает псевдонимы, оставляя одну запись на IP
сервера. [`health.json`](health.json) записывает причину отказа для каждой остальной ссылки.

</details>

<details>
<summary><strong>Чем отличаются MTProto, secure (dd) и FakeTLS (ee)?</strong></summary>

Всё это MTProto-прокси. Секреты `dd` добавляют к трафику случайное заполнение; `ee` (FakeTLS)
маскируют соединение под TLS к выбранному сайту, такой трафик сложнее распознать. Для каждого типа
есть свой уровень: [`secure/`](#tiers) и [`faketls/`](#tiers).

</details>

<details>
<summary><strong>Можно использовать эти списки в своём боте или приложении?</strong></summary>

Да. Используйте [`index.json`](index.json), чтобы узнать текущие пути к файлам, и
[`proxies.json`](resilient/proxies.json) для структурированных данных. Соблюдайте лицензию MIT и
указывайте DB-IP для данных о стране и ASN.

</details>

<a id="honest-limits"></a><a id="security-privacy-and-honest-limitations"></a>

## 🛡️ Безопасность, приватность и честные ограничения

- **Прокси — это не VPN.** Он передаёт только трафик Telegram MTProto и не защищает остальные
  соединения вашего устройства.
- **Оператор видит метаданные подключения**, включая ваш IP-адрес и время. Сообщения при этом
  остаются зашифрованы собственным шифрованием Telegram. Считайте любой публичный прокси
  недоверенной стороной.
- **У результата проверки есть место и время.** Прокси может не работать у вашего провайдера,
  даже если прошёл проверки на раннере.
- **Некоторые публичные прокси показывают спонсорский канал.** Проверка не может определить, что
  прокси покажет после подключения.
- **Страна сервера — не ваша точка доступа.** Списки по странам основаны на GeoIP сервера.
- **Проект независим** и не связан с Telegram и не одобрен им.
